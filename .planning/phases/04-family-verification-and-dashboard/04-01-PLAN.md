## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser (any client, no Firebase Auth) → four new `onCall` Functions | Untrusted; only the WebAuthn ceremony crypto and the HMAC token stand between an attacker and a verdict |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-01 | Spoofing / Elevation of privilege | `answerVerification` | high | mitigate | Server rejects any `answer:'yes'` lacking both a passkey `response` and a `token` (Task 4); WebAuthn assertion is verified server-side via `verifyAuthenticationResponse` before any state mutation, never trusted from the client |
| T-04-02 | Tampering (replay) | `webauthnChallenges/{memberId}` | medium | mitigate | Explicit `expiresAt` TTL (5 min registration / 60s authentication) checked in the finish/answer callables, and the challenge doc is deleted immediately after use |
| T-04-03 | Information Disclosure | `prompts/{memberId}` public-read carries the VER-05 HMAC token | low | accept | Token is single-purpose (tied to one `callId`+`memberId`) and single-use (Task 4's `failed-precondition` guard) — leaking it lets someone answer one specific call, not impersonate the member generally |
| T-04-04 | Spoofing | Cloned-authenticator signature replay | high | mitigate | `authenticationInfo.newCounter` is persisted back onto the stored passkey after every successful assertion (Task 4); a non-increasing counter on a future assertion would be rejected by `verifyAuthenticationResponse` itself |
| T-04-SC | Tampering | `@simplewebauthn/server`/`@simplewebauthn/browser` npm install | high | mitigate | Both flagged SUS (too-new-latest-version only) in RESEARCH's Package Legitimacy Audit; Task 2 is a blocking human-verify checkpoint confirming `repository.url` before Task 3 installs anything — not auto-approvable |

</threat_model>
