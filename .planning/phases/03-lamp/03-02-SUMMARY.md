# Phase 3 Plan 2: Firestore to Lamp Bridge Summary

Deployed a `mirrorActiveCallToLamp` Cloud Function that narrows the closed `calls/{id}` collection into a publicly-readable `lamp/current` doc (state + first name only), a `raiseFamilyAlert` callable for the joystick path, and a Node bridge (`bridge/index.mjs`) that relays Firestore state to the Pi over ethernet and polls the Pi's joystick back into a Firestore alert — proved end-to-end live against the real deployed project and the real Pi hardware from Plan 01, with zero new credentials introduced.

## Decisions Made
- Added `bridge` to `pnpm-workspace.yaml` rather than running a bare `npm install` inside `bridge/`, keeping the whole monorepo on one package manager and letting pnpm link `firebase@12.15.0` from its existing store (already present for `apps/web`).
- Used a short `firebase-admin` + `gcloud auth application-default` script (run from `functions/` so Node resolves the already-installed dependency) as the live-write method for every task's verification, since the Firebase CLI's `firestore:set` command referenced throughout the plan and RESEARCH.md does not exist in this project's installed CLI version (15.22.4) — exactly the fallback the hackathon_rules anticipated.
- Implemented `bridge/write-config.mjs` (a small addition beyond the plan's literal file list) because the plan's action text and the README's documented fallback both describe `pnpm run lamp:bridge:config` as a real, runnable command — leaving it undocumented-but-unimplemented would have shipped a broken instruction.

## Issues Encountered

**Cross-executor Firestore interference during live verification (not a defect).** This plan executed concurrently with another executor building `functions/src/elevenlabs*.ts` / `endCall.ts` against the same live `porchlight-hack` Firestore project. Several times during manual verification, `lamp/current` reflected a `screening` state from the other executor's own real `calls/{autoId}` test writes (visible via unfamiliar `callId` values like `"curl-test-1"` or an auto-generated doc ID) racing with this plan's own test writes to `calls/demo`. This is exactly the intended cross-feature behavior — `mirrorActiveCallToLamp` is deliberately state-agnostic about which call is active — and every deliverable in `coverage` above was re-verified in a tight enough window to attribute the observed Pi/lamp state unambiguously to this plan's own write. No code change was needed; documented here so a reader of a stray Firestore state doesn't mistake it for a bug in this plan's code.

**Inherited from Plan 01: the Pi is running `lamp.py` manually (`nohup`), not via systemd.** Plan 01's Task 4 (systemd install) is `status: halted` on a sudo authentication gate on the Pi, unrelated to anything in this plan. This plan's own requirements (LAMP-02, LAMP-04) do not depend on systemd — the live Pi process answered every HTTP call made during this plan's verification — but the lamp will not survive a Pi reboot/crash until that gate is resolved by a human. Not a blocker for this plan; carried forward as an open item from Plan 01.
