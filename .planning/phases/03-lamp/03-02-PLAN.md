<objective>
Continuing the Plan 01 user story: **so that** a senior never has to read anything, the lamp Plan 01 built now has to actually hear about a real call. This plan wires the cloud/bridge half: a Cloud Function mirrors just the fields the lamp needs out of the closed `calls/{id}` collection into a narrowly public `lamp/current` doc, a small Node script on the Mac watches that doc and relays it to the Pi over the ethernet cable, and the same script polls the Pi's joystick flag and turns a press into a Firestore alert record.

Purpose: close the loop from "a call's state changes in Firestore" to "the lamp changes color," and from "a senior presses the joystick" to "the family gets an alert," without opening Firestore's rules any wider than Phase 1 already closed them and without a service-account secret on the demo laptop.
Output: `functions/src/lamp.ts` (mirror Function), `functions/src/alerts.ts` (`raiseFamilyAlert` callable), updated `firestore.rules`, `bridge/index.mjs` + `bridge/package.json` (the relay script), a root `pnpm lamp:bridge` script.

**Dependency note:** Functions deploy depends on Plan 01-03's human checkpoint (Firebase project creation + Blaze upgrade). If that checkpoint hasn't happened yet when this plan executes, every task's verify has a documented fallback that writes `lamp/current` directly via the Firebase CLI, bypassing the not-yet-deployed Function — the bridge and Pi side are still fully exercised.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Any internet client → `lamp/current` (public `get`) | Deliberately public-read by design; contains only `state` + a first name, no other call data. |
| Bridge (trusted Mac process, public web SDK config) → Firestore | Same trust tier as `apps/web` — no admin credentials, can only do what the public config + rules allow. |
| Bridge → Pi HTTP `POST /state` | Crosses the same direct ethernet link as Plan 01; the bridge is the only writer expected on that link. |
| Client → `raiseFamilyAlert` callable → `households/{id}/alerts` | A callable Function is a real trust boundary — anyone with the project's public config could in principle invoke it, not just the bridge. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-06 | Information Disclosure | `lamp/current` public `get` | low | accept | By design — the document intentionally carries only `state` and a first name so the ambient device can work with no auth; no other call field (transcript, risk detail, phone number) is ever mirrored here (Task 2 enforces the narrow shape). |
| T-03-07 | Tampering | `lamp/current` write path | high | mitigate | `firestore.rules`: `allow write: if false` — only the Admin SDK (the mirror Function) can write it; a client-writable mirror would let anyone on the internet flip the lamp to `scam` mid-demo (Task 1). |
| T-03-08 | Spoofing / Tampering | `raiseFamilyAlert` callable | medium | mitigate | Server-side lookup confirms `householdId` corresponds to a real, existing household before writing anything; unknown IDs are rejected with `not-found` rather than silently writing an alert against a made-up path (Task 3). |
| T-03-09 | Denial of Service | Bridge `fetch` calls (to Pi and to Firestore) | low | mitigate | `AbortSignal.timeout` on every `fetch` (2s to the Pi, 1s to `/joystick`) so a hung network call can't stall the `onSnapshot` callback or the 500ms poll loop indefinitely (Tasks 1 and 3). |
</threat_model>
